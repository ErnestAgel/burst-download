# 交接文档（2026-08-14）— v2.4.x 发布与内嵌 Python 运行时问题

> 本会话核心：修复 v2.4.2 / v2.4.3 在部分 Windows 电脑上“缺少 Python runtime”
> 的问题；**已收敛**：v2.4.6 发布并在另一台电脑验证通过，根因（Windows 非
> UTF-8 区域下窄路径打不开 UTF-8 中文路径）修复闭环；v2.4.2–v2.4.5 已在
> GitHub Release 页标记弃用并指向 v2.4.6（见 §4）。

## 1　背景

- 仓库：`F:\burstdownload\burst-download`（C++17 + ImGui + GLFW），远端
  `https://github.com/ErnestAgel/burst-download.git`，默认分支 `main`。
- 发行物采用**内嵌运行时**：`package_release.py` 把 pyc 化后的
  `third_party/python/runtime`（stdlib / yt_dlp / lib-dynload）打包成 BURSTARC
  blob 追加到 exe 尾部，运行时解包到 `%TEMP%\burst-runtime`。
- 用户反馈：v2.4.2 / v2.4.3 在部分 Windows 电脑上视频解析报“缺少 Python
  runtime / Error Python runtime”；v2.4.1 正常。

## 3　根因与已修复内容（main 上已推送）

### 3.1　v2.4.2 引入的回归（0940f43 修复）

v2.4.2 的 P8/P9 重构重写了内嵌运行时解包，新增了与 v2.4.1 不同的实现：

1. 缓存锁用 `CreateFileA` / `stat` / `remove`（ANSI 窄路径 Win32/CRT API），
   与其余 UTF-8 路径处理不一致，特定系统区域/路径下会失败；
2. 缓存替换是“删旧目录 → rename”，旧缓存被占用（进程/杀软锁定）时整体失败；
3. 锁获取失败**直接返回 false**，运行时被锁问题彻底卡死。

`0940f43` 修复：

- 锁改为 `std::filesystem::create_directory` 目录锁（跨平台、UTF-8 一致），
  且**锁失败不再致命**（tmp+rename 本身保证缓存原子性）；
- 主缓存被占用时自动落到 `burst-runtime-<hash8>` 备用缓存；
- 新增诊断接口 `EmbedRuntimeLastError()` / `EmbedLastInitError()`。

### 3.2　诊断可见性（b7e151b）

`[detail]` 原本只写进任务错误快照、GUI 不展示，导致远端机器只能看到固定文案
“video parsing failed: Python runtime”。现改为：

- Log 面板直接输出 `... - <真实原因>`；
- 悬停任务行 Error 徽标弹出完整错误。

### 3.3　缓存自愈（218cc71）

- 缓存命中校验加强：必须存在 `stdlib/encodings/__init__.pyc` 与
  `yt_dlp/__init__.pyc`，残缺缓存一律重建；
- 若命中后 `Py_Initialize` 仍失败且 home 是缓存目录，自动删除该缓存并
  **重建一次重试**。

### 3.4　其他本次会话改动

- `5618c7a`：URL / 保存路径输入框右键菜单（粘贴/复制/剪切，ImGui 默认无）。
- `b2399b9`：移除 ci.yml 的 assets/ 产物打包（发布固定走内嵌方式）。
- `0ed22d3`：新增手动工作流 **Package (embedded verify)**（`workflow_dispatch`，
  构建三平台内嵌包并上传 artifact，不创建 Release）。
- `2f1e1c5`：版本号 2.4.3 → 2.4.4。

## 4　验证状态（已收敛）

**最终结论（2026-08-14）**：v2.4.6 已在另一台电脑验证通过；v2.4.2–v2.4.5
全部在 GitHub Release 页标记弃用（`[!WARNING]` 横幅指向 v2.4.6），v2.4.0 及
更早版本的弃用横幅目标也统一改为 v2.4.6。

根因闭环（提交 `286e1d3`）：v2.4.2 起 exe 路径改用 `GetModuleFileNameW → UTF-8`，
而解包/初始化仍用 ANSI 窄路径 API（`std::ifstream`/`access()`/`GetTempPathA`），
在 ACP≠UTF-8（如 GBK）且路径含中文的电脑上打不开 exe / 缓存路径错乱，表现为
“no embedded runtime footer” 或 “Py_Initialize failed”。修复统一为
`std::filesystem::u8path`（原生宽路径）+ `GetTempPathW` + filesystem 存在性
检查，与系统区域无关。

关键教训：**测试必须同机对照**。本会话早期“能跑 / 不能跑”的结论混用了不同电脑，
造成大量误导：

- verify zip（Debug 内嵌）在“另一台电脑”解析成功；
- CI assets 版（Release + assets/ 目录）可运行；
- release v2.4.4 在本机（清空 `%TEMP%` 后）报 Error Python runtime —— 但该次
  测试后来确认是**在本机**跑的，不是另一台电脑；
- 用户随后在**另一台电脑**用 run 31775967728 的产物（main，含自愈 + 诊断）
  与正式 v2.4.5 做对照测试，均失败并指向路径编码根因。

已确认事实：

- v2.4.4 在本机：解包成功（`%TEMP%\burst-runtime` 生成且含 stdlib/yt_dlp）；
- 用修复后的本地 harness（链接 `bd311.dll`，避免双 python DLL 实例）验证
  v2.4.4 运行时：`import os/json/ssl/hashlib/socket/yt_dlp` 全部成功；
- 失败电脑上解包成功（缓存存在）→ 失败点在 **Py_Initialize**，真实原因待
  `[detail]` 确认 —— 后经 v2.4.5 另一台电脑日志确认根因是路径编码。

**完成事项**：

1. run 31775967728（main 产物）与正式 v2.4.5 在另一台电脑测试，失败日志指向
   窄路径读不到 exe（“no embedded runtime footer”）；
2. 定位根因（UTF-8 路径 × ANSI 文件 API）并提交 `286e1d3` 修复（v2.4.6）；
3. 发布 v2.4.6（Release 三平台 + GPG 签名），另一台电脑验证通过；
4. v2.4.2–v2.4.5 全部标记弃用指向 v2.4.6；v2.4.0 及更早横幅目标统一为 v2.4.6。

## 5　本地构建与打包

```powershell
$env:PATH = "D:\msys2\mingw64\bin;" + $env:PATH
cd F:\burstdownload\burst-download
cmake --build build-ui --target burst -j 4        # Debug 开发构建

# 内嵌打包（必须 Python 3.11，pyc 需匹配 3.11 运行时）
F:\burstdownload\tools\python-3.11.9-embed\python.exe scripts\package_release.py `
  --platform windows-x86_64 --exe build-ui\burst.exe `
  --runtime third_party\python\runtime --build-dir build-ui `
  --out burst-windows-x86_64-verify.zip
```

注意：Debug 构建会注入 `PYTHON_RUNTIME_FALLBACK`（源码树路径），Release 不注入，
所以**用 Release/CI 产物验证内嵌路径**，Debug 仅用于快速开发。

## 6　CI / 发布工作流

| 工作流 | 触发 | 产物 |
| --- | --- | --- |
| `ci.yml` | push / PR | 仅构建 + 冒烟（版本/帮助/单测/下载回归），**不再上传产物** |
| `package.yml` | 手动（Actions 页面 Run workflow） | 三平台内嵌包 artifact（不发布 Release） |
| `release.yml` | push `v*` tag | 三平台内嵌包 + GPG 签名 + GitHub Release |

## 7　本地验证技巧（复用）

- 解包是否成功：运行 exe 后检查 `%TEMP%\burst-runtime`（stdlib/yt_dlp/manifest）。
- Python 运行时端到端测试 harness（`%TEMP%\burst-pyinit-test`）：
  - 必须用 `gendef bd311.dll` + `dlltool` 生成 `libbd311.a` 并以 `-lbd311` 链接，
    使 harness 与 blob 内 .pyd 共用同一个 Python DLL；
  - **禁止**同时存在 `python311.dll` 与 `bd311.dll`（双实例会导致
    `import ssl` 崩溃——这是 harness 陷阱，不是产品 bug）。
- 版本/提交追溯：`git log --oneline v2.4.3..HEAD`、`git diff v2.4.1 v2.4.4`。
